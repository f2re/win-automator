# Сбор отладки для разработки

Режим **«Сбор отладки»** предназначен не для обычного журналирования, а для воспроизведения проблем пользовательского сценария. Его задача — собрать достаточно контекста, чтобы разработчик видел не только текст ошибки, но и последовательность действий оператора, состояние Windows UI и внутренние решения Win Automator.

## Как запустить

После установки в меню «Пуск» есть отдельный ярлык:

```text
Win Automator — сбор отладки
```

То же самое из portable-каталога:

```powershell
.\WinAutomator.exe --debug-capture
```

## Рекомендуемый порядок

1. Запустите **Win Automator — сбор отладки**.
2. Коротко опишите проблему: что ожидалось и что произошло.
3. Оставьте значения полей и скриншоты выключенными, если они не нужны для диагностики.
4. Нажмите **Начать сбор**. По умолчанию контроллер сам запускает обычный Win Automator внутри диагностической сессии.
5. Воспроизведите проблемный сценарий.
6. Непосредственно перед/после неправильного поведения нажмите **F10**. Это создаст диагностическую точку с UIA/Win32-снимком активного окна.
7. При необходимости поставьте несколько F10-меток.
8. Нажмите **F11** или кнопку **Завершить и создать ZIP**.
9. Передайте `WinAutomator-debug-*.zip` разработчику или приложите к issue.

## Что содержится в ZIP

```text
WinAutomator-debug-<date>-<id>.zip
├── metadata.json
├── context-start.json
├── context-final.json
├── SUMMARY.md
├── manifest.json
├── events-controller-*.jsonl
├── events-executor-*.jsonl
├── events-recorder-*.jsonl
├── events-excel-*.jsonl
└── snapshots/
    ├── snapshot-*.json
    └── window-*.bmp        # только если включены скриншоты
```

### Сырой пользовательский таймлайн

Контроллер фиксирует:

- смену активного окна;
- координаты и тип клика;
- UIA/Win32 fingerprint элемента под мышью;
- `TAB`, `ENTER`, `ESC`, стрелки и другие навигационные клавиши;
- факт и длину текстового ввода;
- паузы между событиями;
- F10-метки проблемы.

При выключенной опции **«Сохранять введённые значения»** сами символы текстового ввода не сохраняются.

### Смысловой таймлайн Recorder

Если проблема воспроизводится во время обучения, пакет дополнительно содержит:

- какой элемент определил Recorder;
- когда `Edit` был превращён в `SET_VALUE`;
- когда `ComboBox + ListItem` был превращён в `SELECT`;
- с каким столбцом Excel совпало введённое значение;
- паузы/завершение обучения.

### Внутренний таймлайн Executor

При выполнении сценария фиксируется:

- начало и результат каждого шага;
- selector, который искался;
- лучший кандидат и его score;
- минимальный допустимый score;
- число рассмотренных кандидатов;
- способ выполнения действия: например `invoke`, `click_input`, `set_edit_text`, `set_text`, `send_keys`, `wrapper.select`, fallback через `ListItem`;
- длительность шага;
- точная ошибка resolver/action.

Это позволяет отличить, например, следующие ситуации:

```text
control вообще не найден
```

от:

```text
control найден, но score=25 при минимуме 30
```

или:

```text
правильный control найден, но set_edit_text не поддерживается и fallback send_keys дал неправильный результат
```

## F10: снимок состояния окна

Для каждой F10-метки записывается отдельный JSON.

Он содержит дерево активного окна через оба backend, когда они доступны:

```text
UI Automation
Win32
```

Для каждого элемента сохраняются:

- `ControlType`;
- `AutomationId`;
- `ControlId`;
- `ClassName`;
- имя/accessibility name;
- прямоугольник на экране.

Количество элементов ограничивается, чтобы диагностический пакет не становился бесконтрольным по размеру.

## Скриншоты

Скриншоты **выключены по умолчанию**.

Если включить соответствующий флажок, F10 дополнительно сохраняет BMP активного окна. Это полезно для custom-drawn интерфейсов, где UIA/Win32 почти ничего не видят, но изображение может содержать персональные или служебные данные.

## Приватность по умолчанию

Без дополнительных флажков режим:

- не сохраняет строки Excel;
- сохраняет только имя Excel-файла, лист, заголовки и число записей;
- не сохраняет имя пользователя Windows;
- не сохраняет имя компьютера;
- не сохраняет текст, который оператор набирал в поля;
- маскирует `name` для `Edit`, `Document` и `ListItem`, где имя часто является самим значением;
- не делает скриншоты.

Для замаскированных значений может сохраняться длина и короткий SHA-256 fingerprint. Это позволяет понять, менялось ли значение, не помещая его в пакет открытым текстом.

Названия окон и accessibility-имена статических элементов сохраняются, потому что без них невозможно восстановить логику оконного сценария. Перед передачей диагностического архива всё равно следует учитывать режим секретности конкретной системы.

## Значения полей

Опцию **«Сохранять введённые значения»** включайте только когда конкретная проблема зависит от преобразования значения и без него проблему невозможно понять.

В этом режиме в диагностическом пакете могут оказаться значения полей и mappings сценария.

## Manifest

`manifest.json` содержит размер и SHA-256 каждого файла внутри пакета. Это позволяет проверить, что отдельный лог или snapshot не был заменён после создания архива.

## Для разработчика

Начинайте анализ с `SUMMARY.md`, затем находите ближайшую `problem_marker` и сопоставляйте события вокруг неё:

```text
user_click / user_text_input
semantic_step
resolver
executor_step
problem_marker
```

После этого откройте соответствующий `snapshots/snapshot-*.json` и сравните реальное дерево окна с selector, записанным в сценарии.

Типовые решения после такого анализа:

- изменить selector scoring;
- добавить ещё один устойчивый признак элемента;
- скорректировать распознавание ComboBox/ListItem;
- добавить конкретный Win32 fallback;
- изменить ожидание появления окна;
- добавить новый semantic action;
- только если UIA/Win32 объективно недостаточны — добавить image/OCR fallback для конкретного класса контролов.
